# study-planner

[![CI](https://github.com/yuwenteng1030/study-planner/actions/workflows/ci.yml/badge.svg)](https://github.com/yuwenteng1030/study-planner/actions/workflows/ci.yml)

想學一樣東西，但不知道「現在最該學什麼」——這個網頁回答這件事。

使用者填下想準備的題型、每天可投入幾小時、希望幾天內完成。網站排出該做哪些項目、每天提醒要完成什麼、並說明**每一項為什麼重要**。

> 開發中。v0.1-core：評分、排程、落後重排、進度記錄、資料匯出與刪除、學習地圖（點關卡就到 HackerRank 做題）皆可運作，306 個測試通過。題庫 125 題，涵蓋知識地圖 20 / 21 個主題。

## 跟「直接問 ChatGPT」有什麼不同

| | 聊天機器人 | study-planner |
|---|---|---|
| 排序依據 | 每次回答都不一樣 | 固定的評分公式，可重現、有 pytest |
| 根據 | 模型印象 | 使用者貼上的 JD，附出處引用 |
| 時間估計 | 猜的 | 從你實際花的時間反推校正 |
| 落後了 | 要自己再問一次 | 自動重排，主動提醒 |
| 沒被選上的項目 | 不會提 | 說得出為什麼沒選（容量不足／分數較低／前置未滿足） |

## 重點題組（先練這 30 題）

題庫 125 題對「先準備上機考」來說太多。依常見的企業上機考型態（3 題、90 分鐘，以陣列／字串處理與 Medium 為主，偶有圖與 DP）挑出 30 題，分三段：

| 段 | 題數 | 內容 |
|---|---|---|
| 暖身 | 6 | Counter／defaultdict、旋轉與重複字串、字串交集、雜湊查表——把語法與輸入輸出練到不卡手 |
| Medium 主力 | 14 | 陣列（New Year Chaos、Sparse Arrays）、字串與雜湊（Sherlock 系列、Count Triplets、Frequency Queries）、排序與二分（Minimum Swaps 2、Fraudulent Activity、Pairs、Minimum Time Required）、Greedy、Stack |
| 進階 | 10 | 圖（Roads and Libraries、Journey to the Moon、BFS）、DP（Max Array Sum、Coin Change、Candies、Common Child）、單調堆疊，加上 3 題 Hard（拿部分分數用） |

合計 Medium 21 題、Hard 3 題、約 1035 分鐘。首頁預設「只排重點題組」，學習地圖預設「只看重點路線」；做完再關掉開關，排其餘的題目。
挑選是 `data/tasks.csv` 的 `focus` 欄（1／2／3），不動評分公式：重點題組只是縮小排程的輸入。

## 評分公式

```
score(topic) = base_weight × jd_factor × gap_factor × goal_factor
```

| 因子 | 範圍 | 說明 |
|---|---|---|
| `base_weight` | 1–10 | 主題本身的重要性（Hash Map 10、兩指標 9、…） |
| `jd_factor` | 1–2 | `1 + (提到該主題的 JD 份數 ÷ 總份數)`；**沒有任何 JD 時固定為 1** |
| `gap_factor` | 0.3 / 1.0 / 1.5 | 已熟／普通／沒學過 |
| `goal_factor` | ×1.3 | 命中使用者目標時加權 |

排序後依百分位切三層：前 40% 必學、次 35% 建議、其餘加分。評分結果用 `data/golden_cases.yaml` 的黃金案例做迴歸測試。

## 架構

```
Streamlit (app/)  →  core/  →  db/repositories.py  →  SQLite
                       ↓
                  llm/client.py  →  Claude API（失敗則回退預存文字）
```

`core/` 是純函式：不碰資料庫、不發 HTTP、不呼叫 LLM，所以測試只需要傳字典。**換資料庫只改 `db/` 這一層。**

五頁：`app/Home.py`（填條件、排計畫）、`app/pages/1_今日任務.py`（打勾、記時間、落後重排）、`app/pages/2_我的資料.py`（匯出、刪除）、`app/pages/3_學習地圖.py`（關卡圖：一關＝一題，一條由下往上的蜿蜒小路；點關卡在新分頁打開 HackerRank 題目，回來按「我 submit 過了」就破關，小熊走到下一關；有計畫時今天的關卡標藍圈、過期的標紅圈，小熊站在今天的第一題，今日任務的每張卡都能「在地圖上看」）、`app/pages/4_回顧.py`（每週／每月完成率、最常落後的主題）。

## 設計決策

每一條都寫「決策／理由／代價」。沒有代價的決策通常是還沒想清楚。

### 1. 四個因子用乘法，不用加法

`base_weight × jd × gap × goal`，不是相加。加法會讓「完全沒提到」與「每份 JD 都提到」只差一個常數，乘法才能按比例拉開。

**代價**：任何因子為 0 都會讓整個分數歸零，所以每個因子都必須有明確下界——這也是 `gap_factor` 的「已熟」是 0.3 而不是 0 的原因。

### 2. `jd_factor` 上限是 2，不是 3

上限代表「JD 最多只能讓一個主題的分數翻倍」。設 3 的話，`base_weight=3` 的冷門主題吃滿加權（3×3=9）就會贏過 `base_weight=8` 的核心主題（8×1=8）；設 2 則是 3×2=6 < 8，JD 只能重排同級主題，不能顛覆基本盤。

**代價**：如果某個主題真的在市場上極度搶手，系統會低估它。

**目前的實作狀況（2026-10-22 查證）**：上限 2 其實是公式**本身的形狀**給的，不是常數給的。`ratio = 提到的份數 ÷ 總份數` 最大就是 1，所以 `1 + ratio` 最大就是 2；`jd_factor()` 裡的 `min(..., JD_FACTOR_MAX)` 永遠不會生效。把 `JD_FACTOR_MAX` 改成 3，計算結果一個數字都不會變。

所以 `test_jd_factor_cannot_overturn_base_weight` 守的是「現在的公式不會讓冷門主題反超」，**不是**「上限必須是 2」：常數改成 3 它照樣是綠的。改成 3 時會紅的只有 `test_jd_factor_is_capped_at_two`，但它是拿輸出值去比常數，紅的原因是「2.0 ≠ 3.0」，跟排序無關。換句話說，常數和公式要**一起**放寬才會出事：只改公式（例如 `1 + 2 × ratio`）的話，夾鉗會開始生效，上限仍是 2，理由照樣成立；公式改成 `1 + 2 × ratio` **而且** `JD_FACTOR_MAX` 改成 3，`test_jd_factor_cannot_overturn_base_weight` 才會紅。

### 3. 用百分位分級，不用固定分數門檻

不寫「score > 10 就是必學」，而是「前 40% 必學」。換領域、調權重、或使用者程度改變時，分數的絕對範圍會整個平移，寫死的門檻每次都要重調。

**代價**：主題數很少時百分位不穩，所以設了「至少 1 筆必學」的下限，否則主題少於 3 個時整張清單會全是「加分」，使用者打開網站看不到任何該做的事。

### 4. v0.1 就帶 `user_id`，但不實作登入

所有使用者資料表都帶 `user_id`、所有查詢都經過 repository 層、身分一律來自 `api/deps.py` 的 `get_current_user()`（目前固定回傳 1）。加欄位很便宜，回頭改所有查詢很貴。

**代價**：現在看起來像沒用的抽象。開放登入時只需要改那一支函式加一個登入頁。

### 5. LLM 掛掉，功能不能減

Claude API 只負責把已知的重點改寫成一句話。沒有 API key、額度用完、呼叫失敗，都回退到 `tasks.static_note` 預存的句子。使用者看到的差別只是文字從客製變罐頭——計畫照排、進度照記。完成一題時的鼓勵訊息也是同一條規則：Claude 寫不出來就用 `core/encouragement.py` 的範本。

**代價**：`static_note` 成了題庫的必填欄位，每加一題都要多寫一句話。
這也是為什麼目標用**下拉選單**而不是自由文字框：自由文字必須先經 LLM 解析才能變成主題清單，LLM 一掛整個表單就送不出去。

### 6. 每日時間上限優先於結束日

重排時如果連「必學」項目都排不完，計畫會**往後延**並明確告知，而不是把多出來的時數塞進最後一天。

每日上限是物理限制——使用者一天就只有那麼多時間；結束日只是期望。曾經寫成相反的優先序，結果 60 分鐘的一天被排了 340 分鐘：測試是綠的、畫面也好看，但照著做不可能完成。

**代價**：使用者會看到「你的計畫需要再 3 天」這種不想看到的訊息。但那是真話，而且是他可以處理的資訊（延長期限、調高每日時間、或接受做不完）。

### 7. 選 SQLite，不是 PostgreSQL

單人、單機、資料量以千筆計，SQLite 是零設定的檔案。連線字串集中在 `db/session.py`，查詢集中在 `db/repositories.py`，換 PostgreSQL 只改這兩個檔案。

**代價**：SQLite 預設不檢查外鍵，必須每條連線各自 `PRAGMA foreign_keys=ON`，否則 `plan_items.task_id` 指到不存在的題目也不會報錯。

### 8. v0.1 切成 core 與 1.5 兩層

原定範圍估約 68 小時，可用工時只有 42.5 小時，是 1.6 倍超載。切割判準只有一條：**砍掉之後，「這跟直接問 ChatGPT 有什麼不同」的答案會不會變弱？** 會就留（評分公式、排程、重排、pytest、黃金案例），不會就延（互動糖衣、LLM 快取、成本記錄、估時校正、排行榜）。

**代價**：第一版 Demo 的功能較少——沒有排行榜、沒有鼓勵動畫、目標是下拉選單而非自由文字。

### 9. 刪除資料的順序寫在 repository 層，不靠 ORM cascade

刪一位使用者的資料要按 `progress_events` → `plan_items` → `plans` → `task_completions` → `users` 的順序，由裡往外，而且用 bulk delete 而不是逐列 `session.delete()`。

理由是現在的 schema 根本沒辦法只刪 `users` 那一列：`User.plans` 沒有 cascade、`plans.user_id` 是 NOT NULL，而 `progress_events` 的 `plan_id` 與 `item_id` 完全沒有被任何 cascade 覆蓋到。加上 SQLite 的外鍵檢查是開著的（設計決策 7 的代價），順序錯了會直接撞 `IntegrityError`。

不用 ORM cascade 是刻意的：cascade 寫在 model 上，哪天有人為了別的需求加一條，刪除行為就會跟著悄悄改變；順序寫在函式裡，改動看得見。

**代價**：加新的使用者資料表時，必須記得同時改這支函式——schema 不會自己提醒。所以 `test_user_data.py` 的刪除測試是在**外鍵檢查開著**的資料庫上跑的：漏掉一張表時它會紅，而不是靜靜留下指向空氣的孤兒列。這條順序是用「把順序反過來、測試要變紅」驗證過的，不是只有註解說它重要。

### 10. 不可還原的動作，把關要在後端

刪除鍵原本寫成 `disabled=not ready`（沒輸入確認字串就按不動）。拿掉了——因為那樣後端那段檢查就永遠跑不到：瀏覽器使用者按不動一顆 disabled 的按鈕，`AppTest` 也直接拒絕點擊。真正的防線會變成只長在前端，而後端那段變成**測不到的死碼**。

現在只留一道關卡，寫在真正執行刪除的地方，所以它跑得到、也測得到（`test_delete_without_typing_the_confirm_word_does_nothing`）。

**代價**：按鈕永遠可以按，看起來不如 disabled 乾淨。但按下去會得到一句明確的「請先輸入…，沒有刪除任何資料」，而不是靜靜地什麼都沒發生。

### 11. 破關靠「我 submit 過了」，不自動同步 HackerRank

點關卡會在新分頁打開 HackerRank 的題目，submit 之後回到地圖按一下才算完成。

能讀到「最近解了哪些題」的網址確實存在（`/rest/hackers/<帳號>/recent_challenges`），但它不是公開 API，而且 HackerRank 的 `robots.txt` 寫的是 `Disallow: /rest/`。對方明說不希望程式去讀的路徑，不因為「只讀自己的資料」就變成可以讀——這跟「不爬求職網站」是同一條線。

完成紀錄分兩處存：題目在進行中的計畫裡而且還沒勾，就勾那個計畫項目（今日任務頁同步打勾）；其餘的寫一筆 `task_completions`。每次按鈕只寫一個地方，否則「計畫完成率」會被地圖上自己跑去做的題目灌水；「取消完成」則把每一個說它做完的地方都清掉，否則那一關還是金色。

**代價**：系統相信使用者——按了就算，不知道是不是真的 AC。對一個自己用的學習工具，這個代價可以接受；要拿來排名或發證書就不行。

### 12. 前置借用後置的分數（有效分數取最大值）

排主題順序時，每一輪只能從「前置都排完」的主題裡挑。舊規則按自己的分數挑，結果高分但有前置的主題常常輪不到：`graphs` 的前置是 `trees` 與 `stacks_queues`，只要其中一個排得太晚，`graphs` 就進不了計畫。實測把基礎主題標成「已經熟」、目標選進階演算法，14 天 × 120 分鐘的計畫一題 `graphs` 都沒有——卡住它的是 `stacks_queues`（7 分，本身不是目標），它一直輸給別的候選，目標權重拉不動它。

現在每個主題用「自己與所有後置的最大分數」來競爭，前置會跟著最想學的後置一起提前。前置順序照舊遵守，只改誰先被挑。同樣的情境，`graphs` 從 0 題變成 6 題（`test_familiar_basics_let_advanced_topics_into_a_short_plan`）。

取最大值，不取加總或平均：加總會讓後置很多的基礎主題（`arrays` 有六個後置）重複得分，那件事 `base_weight` 已經算過了；平均會被低分後置稀釋，拉不動前置。

**代價**：前置會跟高分後置同分，可能排在本身更高分、但沒有高分後置的主題前面。同一個情境裡，換到 `graphs` 的代價是 `dp_1d`、`dp_2d`（也是目標主題）從計畫裡消失，`math_number_theory`、`hashmaps`、`strings` 的題數也變少——容量是固定的，提前一條鏈就有別的被擠掉。同分時用自己的分數決勝，所以高分後置一解鎖就緊接著排。另外，這條規則不會讓「沒標熟」的初學者計畫跳過基礎：目標權重只有 ×1.3，推不過 `base_weight` 8 以上的基礎主題，這是刻意的（同設計決策 2：權重只重排同級，不顛覆基本盤）。

## 排程規則

1. **前置先排**：某主題的題目不得排在它的前置主題的題目之前。
2. **高分先排**：前置都滿足的主題之間，按**有效分數**由高到低。有效分數＝自己與所有後置主題分數的最大值，見設計決策 12。
3. **簡單先排**：同主題內按 Easy → Medium → Hard。
4. **塞不下就丟**：每天總分鐘數不得超過上限，並說得出每一題被淘汰的原因。

第 4 點是刻意的：題庫 125 題共 3790 分鐘，而 10 天 × 60 分鐘 = 600 分鐘，**必須淘汰八成以上**（第一批題庫 44 題 1215 分鐘時是淘汰約一半）。如果題庫總時數小於容量，排程就只是把所有題目原封不動排進去，評分與分級完全不影響結果，核心邏輯會空轉而測試仍然全綠。

兩個相關的設計決策：

- **沒有題目的主題視為透明**：`time_complexity` 刻意維持零題目。如果要求「前置主題必須有題目且已完成」，`sorting`（前置是 `time_complexity`）就永遠排不出來。所以前置關係約束的是**順序**，不是**資格**；而且零成本的節點會優先排掉，以免它壓住後面的高分主題——這一條是**有方向性的**：給 `time_complexity` 加題目會讓 `sorting`、`greedy`（base_weight 都是 8）掉到 `stacks_queues`（7）後面而排不進計畫，所以那個限制寫成了測試 `test_time_complexity_stays_task_free`。
- **自評程度逐主題記錄**：`score` 是連乘式，所有主題乘上同一個 `gap_factor` 等於等比放大，排序完全不變。所以程度必須逐主題存（在 `plans.parsed_goal` 裡），單一的整體程度等於讓 `gap_factor` 失效。

## 估時校正

題庫每題的 `est_minutes` 決定一天排得進幾題，但那是人估的。今日任務頁每題都有「實際花了幾分鐘」，打勾時一起存下；回顧頁的「預估時間準不準」拿它跟預估比，依難度給出「實際 ÷ 預估」的中位數與結論（0.8–1.25 倍算準，每個難度至少 5 筆才下結論）。

**只看不改**：預估值不會因此自動調整。要不要照數據改預估、改多少，是排程的輸入，會直接改變排得進幾題，留給人決定（自動校正的 estimator 排在 v0.2）。

三個會讓數字說謊的地方，算的時候排除掉：

- **沒填的**：輸入框預設是空白，沒填就打勾存的是「沒有數字」，不算。（原本預設是預估值，沒填就會存下一筆假的「剛好準時」，只好把所有等於預估的都丟掉，連真的準時也一起丟。改成空白後不必猜。）
- **同一題重做**：只算第一次。第二次通常快很多，算進來會把預估拉成高估。
- **0 分鐘**：照存（使用者刻意填的），但比例沒有意義，不算。

**目前的數據（2026-10-23）**：還沒有真的練習紀錄（開發時點出來的 3 筆測試打勾已清掉）。結論等累積到每個難度 5 筆以上再寫回這裡。

## 技術

Python 3.14、Streamlit、SQLAlchemy 2.x、SQLite（之後 PostgreSQL）、Claude API、pytest

## 開發

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements-dev.txt   # 執行只需要 requirements.txt；這份多了 pytest 與 ruff

python -m scripts.import_data      # 建表（Alembic migration）並匯入 data/topics.yaml 與 data/tasks.csv
pytest -q                          # 306 個測試
ruff check .                       # lint（CI 也跑這兩行）
streamlit run app/Home.py
```

沒有 `ANTHROPIC_API_KEY` 也能完整執行，說明文字會使用預存版本。有 key 時，排出計畫會替每一題生成一句說明，任務卡會標出這句是「Claude 即時生成」還是「預存說明」。

## 資料庫與時間

- **schema 變更走 Alembic**（`db/migrations/versions/`）。網站第一次開交易時自動 `upgrade head`；改了 `db/models.py` 就要寫一支 migration，`tests/test_migrations.py` 會比對兩邊，對不上就紅。
- **時間戳一律存 UTC，「今天」照使用者的時區**（`users.tz`，預設 Asia/Taipei），只在 `core/clock.py` 換算。不能用 `date.today()`：部署在 UTC 的伺服器上，台灣早上 8 點前會拿到昨天。
- **重排每份計畫每天最多一次**，用條件式 UPDATE 搶 `plans.last_replanned_on`；兩個分頁同時打開也只有一個會寫入。
- **同時只有一份進行中的計畫**由資料庫保證（partial unique index），不只靠程式。
- **Claude 的每日額度存在 `api_usage` 表**，重開伺服器不會歸零。
