# study-planner

想學一樣東西，但不知道「現在最該學什麼」——這個網頁回答這件事。

使用者填下想準備的題型、每天可投入幾小時、希望幾天內完成。網站排出該做哪些項目、每天提醒要完成什麼、並說明**每一項為什麼重要**。

> 開發中。v0.1-core：評分、排程、落後重排、進度記錄、資料匯出與刪除、學習地圖皆可運作，153 個測試通過。題庫 125 題，涵蓋知識地圖 20 / 21 個主題。

## 跟「直接問 ChatGPT」有什麼不同

| | 聊天機器人 | study-planner |
|---|---|---|
| 排序依據 | 每次回答都不一樣 | 固定的評分公式，可重現、有 pytest |
| 根據 | 模型印象 | 使用者貼上的 JD，附出處引用 |
| 時間估計 | 猜的 | 從你實際花的時間反推校正 |
| 落後了 | 要自己再問一次 | 自動重排，主動提醒 |
| 沒被選上的項目 | 不會提 | 說得出為什麼沒選（容量不足／分數較低／前置未滿足） |

## 評分公式

```
score(topic) = base_weight × jd_factor × gap_factor × goal_factor
```

| 因子 | 範圍 | 說明 |
|---|---|---|
| `base_weight` | 1–10 | 主題本身的重要性（Hash Map 10、兩指標 9、…） |
| `jd_factor` | 1–2 | `1 + (提到該主題的 JD 份數 ÷ 總份數)`；**沒有任何 JD 時固定為 1** |
| `gap_factor` | 0.3 / 1.0 / 1.5 | 已熟／普通／沒學過 |
| `goal_factor` | ×1.3 | 命中使用者目標時加權 |

排序後依百分位切三層：前 40% 必學、次 35% 建議、其餘加分。評分結果用 `data/golden_cases.yaml` 的黃金案例做迴歸測試。

## 架構

```
Streamlit (app/)  →  core/  →  db/repositories.py  →  SQLite
                       ↓
                  llm/client.py  →  Claude API（失敗則回退預存文字）
```

`core/` 是純函式：不碰資料庫、不發 HTTP、不呼叫 LLM，所以測試只需要傳字典。**換資料庫只改 `db/` 這一層。**

四頁：`app/Home.py`（填條件、排計畫）、`app/pages/1_今日任務.py`（打勾、記時間、落後重排）、`app/pages/2_我的資料.py`（匯出、刪除）、`app/pages/3_學習地圖.py`（關卡圖：一條由下往上的蜿蜒小路，每關一個進度環，小熊站在下一關）。

## 設計決策

每一條都寫「決策／理由／代價」。沒有代價的決策通常是還沒想清楚。

### 1. 四個因子用乘法，不用加法

`base_weight × jd × gap × goal`，不是相加。加法會讓「完全沒提到」與「每份 JD 都提到」只差一個常數，乘法才能按比例拉開。

**代價**：任何因子為 0 都會讓整個分數歸零，所以每個因子都必須有明確下界——這也是 `gap_factor` 的「已熟」是 0.3 而不是 0 的原因。

### 2. `jd_factor` 上限是 2，不是 3

上限代表「JD 最多只能讓一個主題的分數翻倍」。設 3 的話，`base_weight=3` 的冷門主題吃滿加權（3×3=9）就會贏過 `base_weight=8` 的核心主題（8×1=8）；設 2 則是 3×2=6 < 8，JD 只能重排同級主題，不能顛覆基本盤。

**代價**：如果某個主題真的在市場上極度搶手，系統會低估它。

**目前的實作狀況（2026-10-22 查證）**：上限 2 其實是公式**本身的形狀**給的，不是常數給的。`ratio = 提到的份數 ÷ 總份數` 最大就是 1，所以 `1 + ratio` 最大就是 2；`jd_factor()` 裡的 `min(..., JD_FACTOR_MAX)` 永遠不會生效。把 `JD_FACTOR_MAX` 改成 3，計算結果一個數字都不會變。

所以 `test_jd_factor_cannot_overturn_base_weight` 守的是「現在的公式不會讓冷門主題反超」，**不是**「上限必須是 2」：常數改成 3 它照樣是綠的。改成 3 時會紅的只有 `test_jd_factor_is_capped_at_two`，但它是拿輸出值去比常數，紅的原因是「2.0 ≠ 3.0」，跟排序無關。換句話說，常數和公式要**一起**放寬才會出事：只改公式（例如 `1 + 2 × ratio`）的話，夾鉗會開始生效，上限仍是 2，理由照樣成立；公式改成 `1 + 2 × ratio` **而且** `JD_FACTOR_MAX` 改成 3，`test_jd_factor_cannot_overturn_base_weight` 才會紅。

### 3. 用百分位分級，不用固定分數門檻

不寫「score > 10 就是必學」，而是「前 40% 必學」。換領域、調權重、或使用者程度改變時，分數的絕對範圍會整個平移，寫死的門檻每次都要重調。

**代價**：主題數很少時百分位不穩，所以設了「至少 1 筆必學」的下限，否則主題少於 3 個時整張清單會全是「加分」，使用者打開網站看不到任何該做的事。

### 4. v0.1 就帶 `user_id`，但不實作登入

所有使用者資料表都帶 `user_id`、所有查詢都經過 repository 層、身分一律來自 `api/deps.py` 的 `get_current_user()`（目前固定回傳 1）。加欄位很便宜，回頭改所有查詢很貴。

**代價**：現在看起來像沒用的抽象。開放登入時只需要改那一支函式加一個登入頁。

### 5. LLM 掛掉，功能不能減

Claude API 只負責把已知的重點改寫成一句話。沒有 API key、額度用完、呼叫失敗，都回退到 `tasks.static_note` 預存的句子。使用者看到的差別只是文字從客製變罐頭——計畫照排、進度照記。

**代價**：`static_note` 成了題庫的必填欄位，每加一題都要多寫一句話。
這也是為什麼目標用**下拉選單**而不是自由文字框：自由文字必須先經 LLM 解析才能變成主題清單，LLM 一掛整個表單就送不出去。

### 6. 每日時間上限優先於結束日

重排時如果連「必學」項目都排不完，計畫會**往後延**並明確告知，而不是把多出來的時數塞進最後一天。

每日上限是物理限制——使用者一天就只有那麼多時間；結束日只是期望。曾經寫成相反的優先序，結果 60 分鐘的一天被排了 340 分鐘：測試是綠的、畫面也好看，但照著做不可能完成。

**代價**：使用者會看到「你的計畫需要再 3 天」這種不想看到的訊息。但那是真話，而且是他可以處理的資訊（延長期限、調高每日時間、或接受做不完）。

### 7. 選 SQLite，不是 PostgreSQL

單人、單機、資料量以千筆計，SQLite 是零設定的檔案。連線字串集中在 `db/session.py`，查詢集中在 `db/repositories.py`，換 PostgreSQL 只改這兩個檔案。

**代價**：SQLite 預設不檢查外鍵，必須每條連線各自 `PRAGMA foreign_keys=ON`，否則 `plan_items.task_id` 指到不存在的題目也不會報錯。

### 8. v0.1 切成 core 與 1.5 兩層

原定範圍估約 68 小時，可用工時只有 42.5 小時，是 1.6 倍超載。切割判準只有一條：**砍掉之後，「這跟直接問 ChatGPT 有什麼不同」的答案會不會變弱？** 會就留（評分公式、排程、重排、pytest、黃金案例），不會就延（互動糖衣、LLM 快取、成本記錄、估時校正、排行榜）。

**代價**：第一版 Demo 的功能較少——沒有排行榜、沒有鼓勵動畫、目標是下拉選單而非自由文字。

### 9. 刪除資料的順序寫在 repository 層，不靠 ORM cascade

刪一位使用者的資料要按 `progress_events` → `plan_items` → `plans` → `users` 的順序，由裡往外，而且用 bulk delete 而不是逐列 `session.delete()`。

理由是現在的 schema 根本沒辦法只刪 `users` 那一列：`User.plans` 沒有 cascade、`plans.user_id` 是 NOT NULL，而 `progress_events` 的 `plan_id` 與 `item_id` 完全沒有被任何 cascade 覆蓋到。加上 SQLite 的外鍵檢查是開著的（設計決策 7 的代價），順序錯了會直接撞 `IntegrityError`。

不用 ORM cascade 是刻意的：cascade 寫在 model 上，哪天有人為了別的需求加一條，刪除行為就會跟著悄悄改變；順序寫在函式裡，改動看得見。

**代價**：加新的使用者資料表時，必須記得同時改這支函式——schema 不會自己提醒。所以 `test_user_data.py` 的刪除測試是在**外鍵檢查開著**的資料庫上跑的：漏掉一張表時它會紅，而不是靜靜留下指向空氣的孤兒列。這條順序是用「把順序反過來、測試要變紅」驗證過的，不是只有註解說它重要。

### 10. 不可還原的動作，把關要在後端

刪除鍵原本寫成 `disabled=not ready`（沒輸入確認字串就按不動）。拿掉了——因為那樣後端那段檢查就永遠跑不到：瀏覽器使用者按不動一顆 disabled 的按鈕，`AppTest` 也直接拒絕點擊。真正的防線會變成只長在前端，而後端那段變成**測不到的死碼**。

現在只留一道關卡，寫在真正執行刪除的地方，所以它跑得到、也測得到（`test_delete_without_typing_the_confirm_word_does_nothing`）。

**代價**：按鈕永遠可以按，看起來不如 disabled 乾淨。但按下去會得到一句明確的「請先輸入…，沒有刪除任何資料」，而不是靜靜地什麼都沒發生。

## 排程規則

1. **前置先排**：某主題的題目不得排在它的前置主題的題目之前。
2. **高分先排**：前置都滿足的主題之間，按分數由高到低。
3. **簡單先排**：同主題內按 Easy → Medium → Hard。
4. **塞不下就丟**：每天總分鐘數不得超過上限，並說得出每一題被淘汰的原因。

第 4 點是刻意的：題庫 125 題共 3790 分鐘，而 10 天 × 60 分鐘 = 600 分鐘，**必須淘汰八成以上**（第一批題庫 44 題 1215 分鐘時是淘汰約一半）。如果題庫總時數小於容量，排程就只是把所有題目原封不動排進去，評分與分級完全不影響結果，核心邏輯會空轉而測試仍然全綠。

兩個相關的設計決策：

- **沒有題目的主題視為透明**：`time_complexity` 刻意維持零題目。如果要求「前置主題必須有題目且已完成」，`sorting`（前置是 `time_complexity`）就永遠排不出來。所以前置關係約束的是**順序**，不是**資格**；而且零成本的節點會優先排掉，以免它壓住後面的高分主題——這一條是**有方向性的**：給 `time_complexity` 加題目會讓 `sorting`、`greedy`（base_weight 都是 8）掉到 `stacks_queues`（7）後面而排不進計畫，所以那個限制寫成了測試 `test_time_complexity_stays_task_free`。
- **自評程度逐主題記錄**：`score` 是連乘式，所有主題乘上同一個 `gap_factor` 等於等比放大，排序完全不變。所以程度必須逐主題存（在 `plans.parsed_goal` 裡），單一的整體程度等於讓 `gap_factor` 失效。

## 技術

Python 3.14、Streamlit、SQLAlchemy 2.x、SQLite（之後 PostgreSQL）、Claude API、pytest

## 開發

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

python -m scripts.import_data      # 匯入 data/topics.yaml 與 data/tasks.csv
pytest -q                          # 153 個測試
streamlit run app/Home.py
```

沒有 `ANTHROPIC_API_KEY` 也能完整執行，說明文字會使用預存版本。
